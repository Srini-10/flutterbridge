# ADR-50 — Dart `int` semantics: exact within the safe-integer domain, or loud

- **Status:** Accepted (M11, production-compatibility milestone). Resolves the integer limitation recorded in ADR-0049
  D3a and completes ADR-5 D2; supersedes the "refuse runtime `int` bit operations" position of ADR-0049 D3a.
- **Date:** 2026-09-20

## Context

A Dart `int` is a 64-bit two's-complement integer. A JavaScript number is an IEEE-754 double: exact for integers only up
to 2^53 − 1, with 32-bit bitwise operators. ADR-5 D2 limited *literals* to the safe range; nothing checked what
arithmetic did with them. Every case below was run in Dart and in JavaScript on the same values:

| Source | Dart | Emitted JavaScript before |
|---|---|---|
| `3037000499 * 3037000499` | `9223372030926249001` | `9223372030926249000` (rounded, **silently**) |
| `1 << 40` | `1099511627776` | `256` |
| `0xFFFFFFFF & 0xFFFF0000` | `4294901760` | `-65536` |
| `4294967296 \| 1` | `4294967297` | `1` |
| `7 % -3` | `1` | `-2` — the emitted `((a % b) + b) % b` is wrong for a negative divisor |
| `5 ~/ 0`, `5 % 0` | throws | `Infinity` / `NaN`, and execution continues |
| `x &= mask`, `x <<= n` | 64-bit | raw 32-bit JavaScript (the compound forms had a second, hand-copied lowering) |
| `3037000499 * 3037000499` **written as a constant** | `…001` | folded by the compiler's N6 pass in JS doubles to `…000` *before the generator ever saw it* |

The last row is the worst: no generator-level refusal could catch a value the compiler had already rounded.

## Decision

**The `int` domain is the JavaScript safe integers, |n| ≤ 2^53 − 1. Inside it every `int` operation is exact; the
moment one would leave it, it fails loudly. Nothing is ever silently rounded.**

**D1 — Runtime: checked, exact helpers** (`@bridge/runtime-react`, `internal/num/dart_int.ts`).
`intAdd`, `intSub`, `intMul`, `intTruncDiv`, `intMod`, `intAnd`, `intOr`, `intXor`, `intShl`, `intShr`, `intUshr`,
`intNot`, plus `numMod`/`numTruncDiv` for `double`/`num`. `+ - *` check their result with `Number.isSafeInteger`, which is
sound for safe operands (a true value that fits is computed exactly; one that does not rounds to ≥ 2^53 and is
rejected). Bitwise operations and shifts go through `BigInt` with Dart's 64-bit wrap; `~/` uses exact `BigInt` division
beyond 2^31. Out of domain → `BRG4011`; zero divisor → `BRG4012`; negative shift or non-integer operand → `BRG4013`.
`%` follows Dart (never negative: `7 % -3 == 1`). Negative zero is normalised away, as Dart's `int` has none.

**D2 — Generator: one lowering point.** `lowerNumericOperation` serves binary operators, every compound assignment
(`+= -= *= ~/= %= &= |= ^= <<= >>= >>>=`) and `++`/`--`. Selected by the operands' *resolved* types, never the operator
alone: two `int`s → the checked helper; `%`/`~/` on any other numeric pair → `numMod`/`numTruncDiv`; `bool & | ^` →
`Boolean(Number(a) op Number(b))`; `double` `+ - *` stay plain (IEEE-754 is identical in both languages). An operand of
unknown type is refused for the operators that differ.

**D3 — Compile time: constants are exact or refused.** Two integer literals fold with Dart's 64-bit semantics to a
literal; a constant that divides by zero, shifts by a negative count, or leaves the safe range is a **build-time
diagnostic** (`BRG3002`, citing this ADR) — the "diagnostic before unsafe code" the milestone requires. N6 (constant
folding) no longer folds an `int` `+ - *` whose JavaScript result is not exactly representable, so the expression
reaches the generator intact.

**D4 — `num`.** Arithmetic on a `num` (an `int` or a `double` at runtime) uses IEEE-754, exact for doubles and for ints
in the domain. An `int` beyond 2^53 cannot *arrive* in a `num`, because every `int` operation and literal is checked
first; this is the boundary of the contract, not a hole in it. Interpolating a `num` remains refused (ADR-0049).

## Consequences

- **Readability:** emitted `int` arithmetic is `intAdd(count, 1)`, not `count + 1`. It is the price of the guarantee and
  is stated here rather than optimised away, because a value's range is not knowable at a use site. 56 exact-text
  test pins were updated; each was verified to differ *only* by that substitution (the emitter's own transformation
  applied to the old text reproduced the new output).
- **Performance:** one `Number.isSafeInteger` per operation; `BigInt` only for bitwise/shift and large `~/`.
- **Behaviour change (deliberate):** a program that used to render a rounded number for an out-of-range `int` now throws
  `BRG4011` at that operation. That is the point.
- **Evidence:** 3 477 differential cases generated by real Dart (`tests/dart_int_cases.json`, regenerated with
  `dart run`) over boundary values; components executed in jsdom against Dart's own output (`1 << 40`, masks, `~`, `%`
  with a negative divisor, `~/`, overflow); nine mutations across generator, N6 and runtime, all killed.
- **Not covered:** `int.parse`/`toInt`/`round`/`floor` and other numeric SDK methods (still governed by ADR-0049's
  refuse-what-has-no-lowering rule); `double` formatting beyond `doubleToString`; ints as collection keys (no
  collection lowering yet — ADR-0051).
